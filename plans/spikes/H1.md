# H1 Spike: Windows-এ php-cgi pool (আংশিক)

**ফল: সিদ্ধান্ত হয়নি।** এটা H1-এর আংশিক run। [backlog.md](../backlog.md)-র দুটো pass শর্তের কোনোটাই যাচাই হয়নি:

- **Linux FPM-এর অন্তত 50% request/s:** যাচাই হয়নি। এই PC-তে Linux নেই, তাই FPM baseline নেই। কোনো baseline অনুমান করা হয়নি। WordPress-ও চালানো হয়নি।
- **1 ঘণ্টা load-এ crash বা leak নেই:** শর্ত পূরণ হয়নি। সবচেয়ে লম্বা একটানা load ছিল 300.1 সেকেন্ড। 31টা আলাদা load run মিলিয়ে মোট 3439.3 সেকেন্ড (57.3 মিনিট), আর সেটা একটানা নয়; ছোট probe এই হিসাবে নেই। পরিকল্পিত 1 ঘণ্টার soak শুরুই হয়নি।

Fail-এর প্রমাণও পাওয়া যায়নি। Pool-এর নকশায় কী বদলাতে হবে, সেটা শেষের দিকে আছে।

## এই ফল কতটা ধরা যায়

- **Build:** PHP 8.3.28 **TS** (`zts=1`), `cgi-fcgi`। Spec চায় NTS। NTS-এ কিছু চালানো হয়নি।
- **Site:** একটা plain PHP page আর Laravel-এর `/privacy-policy` (dPanel-এর copy, সেটার নিজের sqlite)। WordPress নয়।
- **Noise:** পুরো সময় অন্য agent এই PC-তে compile করছিল, তাই সংখ্যাগুলো noisy। Batch 2-এ 29টা sample-এর 18টায় `rustc` চলছিল। Laravel run-গুলোর গড় CPU 71-99%।
- **Batch 1-এর noise log অকেজো:** `noise1.csv`-এ সব sample-এ rustc 0, কিন্তু সেটা সত্য নয়। Git Bash `/FI`-কে path বানিয়ে দেওয়ায় `tasklist` প্রতিবার ব্যর্থ হয়েছে। তাই batch 1-এর জন্য ভরসা শুধু `cpu_busy_pct`। সেটা দেখায় 15:47-এর পরের অংশ তুলনায় শান্ত (একটা client-এর run-এ গড় CPU 26-27%, মানে প্রায় এক core)।
- **Windows Defender real-time চালু ছিল।** Exclusion দেওয়া হয়নি।
- **Port:** Spec-এর 9100-9999 নয়, নির্দেশমতো 18000-18899, আর canary 18999।
- **User ও Job:** সব process logged-in user হিসেবে। Site user নেই। Job Object ছিল শুধু পরিষ্কারের জন্য, limit ছাড়া।

এই সংখ্যা পড়ার সময় মনে রাখুন:

- **25 req/s PHP-র ছাদ নয়।** একটা client-এ 11.3 req/s, চারটায় মাত্র 25-এর মতো, অথচ CPU গড়ে প্রায় 55%, আর p50 81 থেকে 140 ms হয়েছে। মানে CPU ছাড়া অন্য কিছু আটকাচ্ছে। সন্দেহ sqlite session write-এ, কিন্তু সেটা **মাপা হয়নি**।
- **Recycle-এর খরচ page-এর ওজনে নির্ভর করে।** Laravel-এ recycle থাকা ও না থাকার পার্থক্য noise-এর নিচে (recycle নেই 21.7, আছে 24.5-25.4)। Plain page-এ একটা worker 500 request প্রায় 0.1 সেকেন্ডে শেষ করে, তাই throughput প্রায় চার ভাগের এক ভাগ হয়েছে (16151.8 থেকে 4272.1)।
- **Spare ও stagger-এর লাভ 4 worker-এ প্রমাণিত নয়।** Batch 1-এ দুই round-এ counted 19.8, 18.4; spare 20.9, 16.4; stagger 25.5, 20.6 req/s। Round-এর ভেতরের ফারাক mode-এর ফারাকের সমান।

### Recycle

- php-cgi ঠিক 500 request-এর পর বেরোয়, exit code 0। তিন round-এ তিনবারই।
- **501তম request connect হয়, তারপর reset খায়** (`ConnectionReset/10054`, প্রায় 2.3 ms পর)। মানে connect সফল হলেও request মরতে পারে, আর তখন request পাঠানো হয়ে গেছে। তাই এটা নিরাপদে retry করা যায় না।
- Spawn থেকে listen: প্রায় 57-99 ms, চাপ ছাড়া (আগের run-এর 210 ms ভুল ছিল, নিচে দেখুন)। Worker বেরোনোর পর একই port-এ সঙ্গে সঙ্গে আবার bind হয়, 62.5 ms-এ।

Recycle-এ হারানো request (request পাঠানোর পরের ব্যর্থতা):

| পদ্ধতি | Recycle | হারানো request |
| --- | --- | --- |
| Gateway গোনে, connection প্রতি request (`t-plain-short`, `p-counted`, `l-counted`, `l-stagger`, `l-w1`, `l-q16`, `b-l-counted`, `b-l-stagger`) | 175 | 0 |
| Spare, connection প্রতি request (`l-spare`, `l-w1-spare`) | 12 | 0 |
| `PHP_FCGI_CHILDREN=4`, এক port | সংখ্যা জানা যায় না (Laravel-এ 13টা আলাদা PID দেখা গেছে) | 0 (26,579 request-এ) |
| Naive, gateway গোনে না | plain 24, Laravel 8 | plain 24, Laravel 2 |
| Keep-alive, PHP নিজে বেরোয় | `p-keep` 65, `p-keep-spare` 296, `b-p-keep` 178, `l-keep` 4 | 55, 90, 8, 0 |
| Keep-alive, gateway নিজে idle worker থামায় (`--retire`) | plain 141 ও 226, Laravel 8 | 0, 0, 0 |

দুটো কথা পরিষ্কার:

1. **`flags=0`-এ gateway গুনলে recycle-এ কিছু হারায়নি।** না গুনলে প্রায় প্রতি recycle-এ একটা request হারাতে পারে।
2. **`FCGI_KEEP_CONN`-এ PHP-কে নিজে বেরোতে দেওয়া নিরাপদ নয়।** এক connection-এর probe-এ 6 বারের 1 বার শেষ response আংশিক এসে reset খেয়েছে (`limit=5 ok=4 partial=2155`)। ঠিক কেন, সেটা বের করা হয়নি। `p-keep`-এ একটা request 150 সেকেন্ডের read timeout পর্যন্ত ঝুলেও ছিল (`Read:TimedOut/10060`); এটা আর হয়নি, কারণও জানা নেই।

Keep-alive-এর লাভ: TIME_WAIT প্রায় থাকে না (321-এর মতো, connection প্রতি request-এ 7 সেকেন্ডে 25 হাজার)। Laravel-এ latency-র লাভ স্পষ্ট নয়।

### Opcache ও cold start

Opcache-এর memory একই `cache_id`-এর process-গুলো ভাগ করে, আর সেটা বাঁচে ততক্ষণ, যতক্ষণ অন্তত একটা process জীবিত। প্রতি round-এ `opcache_start` দেখে এটা যাচাই হয়েছে।

| অবস্থা | প্রথম Laravel request (ms) |
| --- | --- |
| আর কোনো process নেই | 1070.7, 984.3, 1537.7, 876.4, 884.1 |
| আরেকটা process জীবিত | 120.7, 130.3, 271.3, 133.9, 113.7 |
| পরের request (দুই ক্ষেত্রেই) | প্রায় 86-186 |

Pool-এ এর ফল:

- **1 worker-এর site:** প্রতি recycle-এ সব process চলে যায়। `l-w1`-এ replacement-এর প্রথম request-এর p50 782.41 ms, spare সহ `l-w1-spare`-এ 101.84 ms (প্রতিটা একবার করে, 4টা recycle; এই p50-এ শুরুর একটা cold request-ও মিশে আছে, তবে 5টার মাঝের মান recycle-এরই)।
- **4 worker একসঙ্গে recycle:** Opcache হারানোর আশঙ্কা ছিল, কিন্তু **হারায়নি**। `b-l-counted`-এ replacement-গুলোর প্রথম request 172, 194, 210, 243 ms। এটা একটা মাত্র wave-এর ফল।
- **Reboot-এর পর প্রথম load:** `b-l-counted` শুরুতে প্রায় 37 সেকেন্ড কোনো request শেষ করেনি, সবচেয়ে ধীরটা 38556.82 ms। CPU প্রায় 100%, rustc চলছিল, আর reboot-এর পর এটাই প্রথম Laravel load। চারটা worker একসঙ্গে cold ছিল, disk cache ফাঁকা ছিল আর Defender হয়তো file scan করছিল: এগুলো **অনুমান**, প্রমাণ নয়। ঘটনাটা একবারই দেখা গেছে। Spec-এর queue 30 সেকেন্ড, তাই এমন হলে queue-তে থাকা request `503` পেতে পারে।

### Queue

- **Pool-এর queue:** 4 worker, 12 request, `sleep(3)`: 3, 6, 9 সেকেন্ডের ঢেউয়ে শেষ, মোট 9.045 সেকেন্ড।
- **`503`:** 4 worker `sleep(40)`-এ, আরও 3 request: 30.002-30.013 সেকেন্ডে `503`।
- **php-cgi-র নিজের queue:** ব্যস্ত worker-ও সঙ্গে সঙ্গে connect নেয় (1 ms-এর নিচে), request kernel-এর backlog-এ বসে থাকে। 128টা connection পর্যন্ত নেয়, তারপরেরগুলো 1.5 সেকেন্ডের timeout-এ আটকায়। **তাই connect সফল মানে worker ফাঁকা, এটা ভাবা যায় না।**
- **Backlog-এ বসা request recycle-এ মরে:** limit 2-এর worker-এ 6টা request পাঠালে 2টা পূর্ণ হয়, 4টা reset খায়। দুবার চালিয়ে দুবারই একই ফল।
- **`l-q16` (16 client):** req/s 26.0, p99 9391.37 ms, max 19159.12 ms। এই tail-এর বড় অংশ **harness-এর দোষ**: এর queue `Condvar` দিয়ে, FIFO নয়, তাই কেউ কেউ বারবার পিছিয়ে গেছে। `php_cgi_pool.rs` tokio-র `Semaphore` ব্যবহার করে; সেটার queue এখানে মাপা হয়নি।

- `l-kill`: 120 সেকেন্ডে 12টা busy worker kill, 14টা request হারিয়েছে (kill-এর চেয়ে 2টা বেশি; কারণ বের করা হয়নি), 3004টা সফল। 10টা connect refuse retry-তে সামলানো গেছে। Max latency 3647.79 ms।
- Crash ধরতে kill-এর পর 10-30 ms লেগেছে (একবার 290 ms), 20 ms poll সহ। Listen-এ ফিরতে p50 64.6 ms, backoff বাদে। Backoff-এর মান (1, 2, 4, 8, 16 সেকেন্ড) spike-এর নিজের, spec-এ নেই।
- `l-policy`: 3 সেকেন্ড পরপর kill, 15.04 সেকেন্ডে পঞ্চম crash-এ site down। বাকি সময়ে 8754টা request সঙ্গে সঙ্গে `503` পেয়েছে। Harness-এ ফেরার পথ ছিল না, spec-ও এটা বলে না।

### TIME_WAIT

drust-এর মতো প্রতি request-এ নতুন connection দিলে PHP আগে বন্ধ করে, আর TIME_WAIT জমে worker port-এ। প্রায় 4600 req/s-এ 7 সেকেন্ডে 24,931টা, সর্বোচ্চ দেখা গেছে 35,044। সেগুলো প্রায় 2 মিনিটে শেষ হয়। ওই পর্যন্ত কোনো connect error হয়নি, আর port 80 ও 9500 সাড়া দিয়েছে। এর চেয়ে বেশি ইচ্ছা করে ঠেলা হয়নি।

Laravel-এর হারে এটা সমস্যা নয় (প্রায় 2900)। হিসাবে, 1000 req/s একটানা চললে প্রায় 120,000 জমবে; সেটা **মাপা হয়নি**।

### Port ভাগাভাগি

- একই user-এর দ্বিতীয় php-cgi একই port-এ bind করে, চুপচাপ চলতে থাকে, কোনো error নেই। দুবার চালিয়ে একই ফল।
- 40টা request-এর 40টাই প্রথম process পেয়েছে। প্রথমটা থামালে দ্বিতীয়টা উত্তর দেয়।
- `php_cgi_pool.rs`-এর `reserve_port` এই কারণেই `SO_REUSEADDR` ছাড়া bind করে। তবে ওই check আর php-cgi-র bind-এর মাঝে সময় আছে, আর চলন্ত worker-এর ওপর আরেকটা process বসতে পারে।
- FastCGI-তে পরিচয় যাচাই নেই। Harness সরাসরি এই port-এ connect করে নিজের বেছে নেওয়া script চালিয়েছে। অন্য user-এর ক্ষেত্রেও একই হবে কি না, সেটা **মাপা হয়নি**, কিন্তু loopback TCP-তে file permission-এর আড়াল নেই। H2 ও J4-এ এটা সরাসরি পরীক্ষা করতে হবে।

### `PHP_FCGI_CHILDREN=4`

php-cgi নিজে এক port-এ 4টা child চালায়। সবাই একই listener ধরে থাকে, তাই একটা child বেরোলে backlog মরে না। এজন্যই recycle-এ কিছু হারায়নি (plain 22,004 ও Laravel 4575 request)।

- Child kill করলে parent 26 ms-এ নতুন child চালিয়েছে।
- Parent kill করলে child-রা প্রায় 10 ms-এ চলে গেছে (এই পরীক্ষায় harness-এর Job Object-ও ছিল)।
- দাম: gateway আর দেখে না কোন worker ব্যস্ত, কোনটা কতটা request নিল, কোনটা crash করল। Load-এ kill loop এই mode-এ চালানো হয়নি।

### Laravel-এর outbound call

`/privacy-policy` request-এ Laravel `GET /capabilities` পাঠায়: batch 2-তে 38 বার। Copy-র `.env` এটাকে live port 9500-এ পাঠাত, তাই spike-এ সেটা 18999-এর canary-তে ফেরানো হয়েছিল। Canary সঙ্গে সঙ্গে connection বন্ধ করে, তাই আসল drust-এর উত্তরের সময় এই latency-তে নেই। Port 9500-এ কোনো connection যায়নি, এটা আলাদাভাবে গোনা হয়নি; ভরসা override আর canary-র ওপর।

## Spike-এর নিজের ভুল

ফল যেন ভুল না পড়া হয়, তাই এগুলো লেখা থাকল:

- **Spawn-এর 210 ms ভুল ছিল।** প্রথম probe-এ readiness check-এর connect timeout 200 ms ছিল, তাই সংখ্যাটা timeout-এই আটকে ছিল। আসল মান প্রায় 65 ms।
- **`PHP_FCGI_CHILDREN=4`-এ 9টা process ভুল ছিল।** সেগুলোর মধ্যে conhost ছিল। প্রথম kill পরীক্ষায় হয়তো php-cgi-র বদলে conhost মরেছিল। Exe-র নাম দেখে আবার চালানো হয়েছে।
- **"একসঙ্গে recycle-এ opcache হারায়" ধারণা ভুল ছিল।** Batch 1-এর `first_request` p50-তে শুরুর 4টা cold request মিশে ছিল। আলাদা করে মেপে batch 2-এ ধারণাটা বাদ পড়েছে।
- **Batch 1-এর noise log অকেজো** (ওপরে), আর **`l-q16`-এর tail harness-এর queue-র দোষ** (ওপরে)।
- `p-keep`-এর guard আগের run-এর TIME_WAIT গুনেছিল। পরে guard শুধু নিজের port গোনে, তবু run-গুলোর মাঝে drain-এর জন্য অপেক্ষা করা দরকার ছিল।

## সিদ্ধান্ত

**H1: সিদ্ধান্ত হয়নি।** Pass দেওয়া যায় না, কারণ দুটো শর্তের কোনোটাই যাচাই হয়নি। Fail দেওয়াও যায় না, কারণ 57.3 মিনিটের বিচ্ছিন্ন load-এ php-cgi নিজে থেকে একবারও crash করেনি, PHP কোনো error লেখেনি, আর recycle-এর আচরণ সামলানো যায়। Pool-এর মূল নকশা (এক process, এক port, gateway গোনে) এই আংশিক run-এ বাতিল হয়নি।

Full H1-এর জন্য বাকি: NTS build, WordPress, একই hardware-এ Linux FPM baseline, শান্ত machine-এ একটানা 1 ঘণ্টা load, ও সম্ভব হলে site user ও Job Object-এর ভেতরে।

## F2-এর নকশায় যা বদলানো দরকার

`edge_gateway/php_cgi_pool.rs`-এর কিছু অংশ এই ফলের সঙ্গে আগেই মেলে: gateway request গোনে, `flags=0`, এক process এক port, `reserve_port`-এর check, `PHP_FCGI_CHILDREN=0`, `Semaphore`-এর queue। এগুলো রাখুন। Code পড়ে দেখা হয়েছে, চালিয়ে নয়। বদলানো দরকার:

1. **Readiness check বদলান।** `start_worker` সাধারণ `TcpStream::connect` করে। PHP listen করার আগে connect গেলে Windows প্রায় 500 ms পরে আবার চেষ্টা করে। `readyblock` probe (`std`-এর connect, 8 বার): 504-526 ms, আর 10 ms timeout-এর poll-এ 58-68 ms। Worker request-এর পথেই চালু হয়, তাই প্রতি worker চালুতে প্রায় 450 ms বাড়তি লাগার কথা। `tokio`-র connect দিয়ে মাপা হয়নি, তাই বদলের আগে-পরে সেটা মেপে দেখুন। Connect-এ ছোট timeout দিয়ে poll করুন।
2. **Worker চালুর সময় পুরনো process-এর অপেক্ষা করবেন না।** 1 worker-এর site-এ পুরনোটা যাওয়ার আগে নতুনটা চালান। না হলে প্রতি 500 request-এ opcache যায় (প্রথম request প্রায় 780 ms, spare সহ প্রায় 100 ms)।
3. **`connect_fpm`-এর retry আবার ভাবুন।** Windows-এ refuse আসতেই প্রায় 2 সেকেন্ড লাগে, তাই 100 ms-এর retry আসলে 2 সেকেন্ডের। Worker মরলে একই port-এ retry না করে নতুন lease নিন।
4. **`FCGI_KEEP_CONN` এখন চালু করবেন না।** চালু করতে চাইলে PHP-র limit 0 দিয়ে gateway-কে idle worker থামাতে হবে (হারিয়েছে 375 recycle-এ 0)। তখন exit code 1 আসবে, তাই crash চেনার কাজ exit code-এ নয়, pool-এর state-এ রাখুন, যেমন এখন আছে। আগে `fastcgi_finish_request()` পরীক্ষা করুন: Response শেষ মানেই PHP-র কাজ শেষ নয়, আর এই পথে worker kill হলে সেই কাজ মরতে পারে।
5. **Process flag ঠিক করুন।** `php_cgi_command`-এ `creation_flags` নেই। `DETACHED_PROCESS` দিন। Flag ছাড়া service থেকে চালালে কী হয়, সেটা মাপা হয়নি, তাই conhost আছে কি না service হিসেবে যাচাই করুন।
6. **নিজের ini দিন।** Command-এ `-c` নেই, তাই এই PC-তে wamp-এর ini load হওয়ার কথা: Xdebug চালু, log `c:/wamp64`-এ। Pool-এর জন্য নিজের ini দিন, আর site অনুযায়ী `opcache.cache_id`। `cache_id` ছাড়া live `php -S`-এর সঙ্গে opcache ভাগ হয় কি না, সেটা মাপা হয়নি; একই user-এর site-গুলোর ক্ষেত্রেও একই প্রশ্ন।
7. **Hang-এর সীমা দিন।** `php.rs`-এর deadline 3600 সেকেন্ড। ঝুলে যাওয়া একটা request এক ঘণ্টা একটা slot আটকে রাখতে পারে। Keep-alive-এ 150 সেকেন্ডের ঝুলে থাকা একবার দেখা গেছে; `flags=0`-এ দেখা যায়নি।
8. **আসল php-cgi দিয়ে test লিখুন।** এখনকার test stand-in process-এ। কমপক্ষে: ঠিক 500-এ exit, 501তম request কখনো না যাওয়া, busy kill, আর response-এর মাঝে kill। Buffered পথে reset `?`-এ error হয়ে ফেরে, কোড পড়ে এটা ঠিক মনে হয়। 1 MB-র বড় streaming response-এ client-এর কাছে আংশিক data চলে যাওয়ার পর কী হয়, সেটা দেখুন।
9. **Job Object আগের মতোই বাকি।** Spike-এ `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` সহ 1345টা process চলেছে, কিছু ফেলে যায়নি, তবে তাতে harness-এর হঠাৎ মৃত্যু পরীক্ষা হয়নি।
